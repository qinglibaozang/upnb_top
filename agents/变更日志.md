## 更新时机

- **每次提交时**：若本次改动包含"用户/维护者可见的变化"，必须在同一次提交中更新项目根 `CHANGELOG.md`（与代码一起提交，日志永不滞后）。
- 纯内部改动（格式化、重命名未发布文件、注释、无行为变化的整理）不记。

## 记录范围（决策 1：只记可见变化）

必须记录：

- 新增/删除内容分类、页面、功能（新增链接卡片类型、自定义页面等）
- 导航/侧边栏/站点身份变化（站名、logo、导航结构）
- 布局/样式体系变化（影响读者观感）
- 依赖增删或升级（影响构建/运行）
- 构建/部署流程变化
- 修复影响使用的问题
- 项目规则/文档体系的重要变化（AGENTS.md、规则文件）

跳过（噪音，不记）：

- 纯文案措辞微调
- 格式化/拼写修正
- 无行为变化的内部重构

## 记录粒度（功能更改要详细）

- **一般改动**：一行概括即可（`- 描述`）。
- **功能更改**（新增卡片类型、新页面类型、新交互、新数据结构生效等）：必须**详细记录**——写清是什么功能、怎么用、影响哪些内容/入口。示例：

```markdown
### 新增
- 新增"工具卡片"类型：支持 icon/title/description/url 字段，
  通过 frontmatter 配置，在资源页以卡片网格展示（见 agents/数据结构.md）
```

## CHANGELOG 格式

项目根 `CHANGELOG.md`，按日期倒序分组，每组用 `###` 分类型（新增/变更/修复）：

```markdown
# 更新日志

## 2026-08-14
### 新增
- 描述
### 变更
- 描述
### 修复
- 描述
```

- 日期格式 `YYYY-MM-DD`，同一天多次提交合并到同一组，按 `###` 类型归类。
- 已有当天分组：追加条目，不新建组；无当天分组：在文件顶部新建。

## 流程

1. 提交前检查改动：有可见变化 → 更新 CHANGELOG.md。
2. 功能更改 → 详细写（功能/用法/影响）。
3. 与代码同一次 `git commit` 入库。
